# There's an LLM Between You and Your Data (And That Changes Everything)

Every major AI lab is racing to build the smartest model. But here's what that race is obscuring: the frontier models are all remarkably good. They can reason, synthesize, and generate at a level that would have seemed impossible two years ago — and the gaps between them are narrowing fast. So if the model isn't the bottleneck anymore, what is? The answer is something far less glamorous but far more consequential: the data your model can actually see, and how that data has been organized and made *meaningful* before the model ever touches it. For years, Microsoft has given developers and enterprises API access to the raw signals of work — emails, calendars, Teams conversations, SharePoint sites, OneDrive files — through the Microsoft Graph. That access was powerful, but it was just data: structured endpoints returning documents and metadata. What Microsoft has been building more recently is something fundamentally different. They've layered a semantic model on top of that raw data — a continuously updated understanding of not just *what* exists across your Microsoft 365 environment, but how it all relates: which people connect to which projects, which conversations led to which decisions, which documents matter right now and why. They call this intelligence layer Work IQ, and it represents Microsoft's bet that in a world where every enterprise will have AI agents operating on its behalf, the real advantage isn't the agent's reasoning ability — it's the richness and structure of the context it reasons over.

To understand what this semantic layer actually changes, consider what happens when an AI agent needs to answer a seemingly simple question: "What's the latest on Project Aurora?" If that agent is built on the Microsoft Graph API, it has work to do. It needs to know which endpoints to query — maybe SharePoint for documents, Outlook for emails, Teams for chat threads — then it has to call each one, parse the results, and try to piece together a coherent picture from what are essentially disconnected data sources. The agent gets back files, messages, and metadata, but none of it comes with any understanding of what's relevant, what's recent in a meaningful sense, or how these signals relate to each other. The reasoning burden falls entirely on your agent. Now contrast that with what happens when the same question is routed through Microsoft's semantic layer — whether via the Copilot Chat API or a Work IQ MCP server. The agent isn't querying raw endpoints anymore. It's tapping into a layer that has already done the work of connecting the dots across your M365 environment. It knows that Project Aurora spans a specific set of documents, a Teams channel, a series of recent meetings, and a handful of key people — and it can surface what's most relevant right now based on that web of relationships. The data that comes back isn't just data. It arrives with context already woven in. That distinction — between retrieving information and receiving understanding — is the architectural fault line that the rest of this series will explore.

This distinction raises an architectural question that most developers building AI agents on Microsoft 365 haven't fully confronted yet: where should the intelligence live? On one end of the spectrum, you go direct — your agent calls the Graph API, retrieves raw data, and owns every step of the reasoning process. You have full control over what gets queried, how results are interpreted, and what actions get taken. But you're also starting from scratch every time, with no benefit from the semantic relationships Microsoft has already mapped. On the other end, you lean into the intelligence layer — routing queries through Copilot-backed services that return semantically enriched responses grounded in the full context of your working environment. Your agent gets richer inputs with less effort, but you've now introduced a second layer of AI reasoning into the pipeline that you don't control and can't fully inspect. Your model is reasoning over output that another model has already shaped. And between these extremes sit approaches that try to balance both — tapping into the semantic index for context while preserving your agent's autonomy over how that context is used. There is no single right answer here. Each approach carries real tradeoffs in control, transparency, data scope, and what your agent can ultimately do. Over the course of this series, I'll be pulling apart four distinct architectural approaches to accessing Microsoft 365 intelligence — from raw Graph API access to the Copilot Chat API, the Copilot Retrieval API, and a Work IQ MCP server — building working demos of each and examining what they reveal about where enterprise AI is actually heading. The question isn't which model to use. It's what sits between the model and your data, and whether you get to decide.
